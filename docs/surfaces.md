# Where GLPI says it is GLPI

This is the inventory the plugin was built from: every place the product's own
identity reaches a user, what covers it, and — for the ones nothing covers —
why not.

It was compiled by walking the login page, the technician interface and the
self-service portal in a browser and reading back every text node, image and
`<link>` that mentioned GLPI. That method is worth repeating after a GLPI
upgrade, because this list is a fact about a version rather than about the
software in general. `glpi-whitelabel/tests/browser/wl-check.js` asserts most of it.

## Covered

| Surface | How |
|---|---|
| Browser tab title, every page | `$CFG_GLPI['app_name']`, set during plugin init |
| Notification footers — *"Automatically generated by GLPI"* | the same, read by `NotificationTemplate` |
| Two-factor enrolment label, as stored in the authenticator app | the same, read by `TOTPManager` |
| Sidebar logo | `--glpi-logo-light` / `--glpi-logo-dark` |
| Collapsed sidebar logo | `--glpi-logo-*-reduced` |
| Login and password-reset card | `--glpi-logo-*-login` |
| About dialog logo | `content:` on the `<img>`, which is not a background |
| Browser tab icon | a `<link rel="icon">`, plus JavaScript to remove core's |
| *"GLPI internal database"* on the login form | JavaScript, in both the `<option>` and the select2 widget over it |
| Version and copyright line | `a.copyright`, hidden by CSS or re-prefixed by JavaScript |
| Help links in both interfaces | core's own `central_doc_url` / `helpdesk_doc_url` |

## Two orderings that decide the design

Both of these are the same lesson: **a plugin is loaded before core finishes
speaking**, so anywhere core states its identity last, the plugin has to
outrank it rather than merely follow it.

**The stylesheet.** Plugin header tags render at line 64 of
`templates/layout/parts/head.html.twig`; core's CSS links render at line 70.
Core declares `--glpi-logo-*` on `:root`, and a later declaration of equal
specificity wins — so a plugin stylesheet saying `:root { --glpi-logo: … }` is
silently overruled. The fix is `:root:root`, which doubles the specificity and
settles it without `!important`, leaving that tool available to a site's own
custom CSS.

**The favicon.** Core writes `<link rel="shortcut icon">` at line 76, after
everything a plugin may inject. Browsers disagree about whether the first or the
last icon wins, so adding one is not enough; core's has to be removed from the
page, which only JavaScript can do.

## Not covered, and why

- **The word "GLPI" inside GLPI's own translated strings.** There are a few, in
  places like error messages. Reaching them means overriding core's gettext
  domain, which would put this plugin in the business of shipping translations
  for a product it does not own — and would break on every language GLPI adds.
- **Anything a user typed.** The plugin never searches a page for the word
  "GLPI" and replaces it. Every substitution is anchored to a selector that
  identifies core's own chrome, because the blanket approach eventually rewrites
  a ticket whose author mentioned GLPI, a knowledge article about migrating off
  it, or a customer whose company has it in the name.
- **The source, the licence headers, the API responses.** Rebranding what a
  developer sees is not what this is for.

## On hiding the copyright

The plugin can hide the version and copyright line, and does not do so by
default. GLPI is GPL, and the licence has things to say about removing
authorship notices. Whether hiding it inside your own helpdesk is a problem is a
question about your situation and your lawyer, and the switch exists so that the
decision is yours to make explicitly rather than one the plugin quietly makes
for you.
